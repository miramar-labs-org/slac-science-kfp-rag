# run-003 — Status Log

**Started:** 2026-07-17 (post run-001/run-002 diagnosis)

Changes from run-002:
- No corpus/eval_dataset changes — same 9-doc corpus, same 36-row eval set as run-002.
- **Root-cause fix**: `gpt-oss:20b` is a reasoning model whose hidden chain-of-thought
  tokens count against the same `max_tokens` budget as the visible JSON verdict. The judge
  calls in `generation_eval` and `faithfulness_eval` had too small a budget (150 / 300),
  so the model frequently exhausted it on reasoning before emitting any/complete JSON,
  hitting `finish_reason: "length"` and falling back to hardcoded default scores
  (`answer_correctness=3.0`, `fact_coverage=0.5`, `faithfulness=3.0`) — this is what was
  actually driving the `relevancy` gate failures in run-001 and run-002, not corpus
  thinness or density.
- Fix: raised judge `max_tokens` — `generation_eval` 150→600, `faithfulness_eval` 300→700
  (`safety_eval`'s 150→500 had already landed earlier in the diagnosis). Confirmed via live
  curl against the Ollama endpoint that 600/700 leaves comfortable headroom for reasoning +
  JSON on both simple and harder multi-fact prompts.
- Goal: confirm judge failures disappear (near-zero `Judge error` / `Faithfulness judge
  error` log lines) and get the first non-fallback-masked measurement of this pipeline's
  actual `relevancy`/`avg_fact_coverage` quality.

Backend: Ollama `gpt-oss:20b` on DGX, used for both generation and judging (self-judging
trade-off, unchanged from run-001/run-002). Reloaded after a DGX power event earlier this
session; confirmed resident (15.8 GB) before triggering this run.

MLflow UI (live metrics): http://localhost:5000
